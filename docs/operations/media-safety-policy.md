# Media Safety Policy

## Purpose

This runbook defines the media safety policy for the Time Archive MVP. It
covers what is already enforced by the application, what operators must do
before approving uploaded media, and when automatic malware scanning becomes a
required production control.

The policy is intentionally conservative: uploaded media is always untrusted
until it passes server-side validation and an admin explicitly approves it.

## Current Enforcement

The application currently enforces the following controls before a media asset
can enter moderation:

- Uploads use server-created, short-lived presigned PUT URLs.
- Object keys are generated by the server.
- Upload completion verifies ownership.
- Upload completion verifies upload request expiration.
- Upload completion verifies object existence in storage.
- Upload completion verifies expected content length.
- Upload completion verifies expected content type metadata.
- Upload completion validates supported file signatures against the requested
  content type.
- Video upload completion validates that detected MP4 duration fits inside the
  owned time range.
- Upload completion rejects invalid uploads before creating a media asset.

The application currently enforces the following controls before media can
appear on the public timeline:

- Original uploaded objects remain private.
- Only `APPROVED` media can appear in public timeline reads.
- `UPLOADED`, `PENDING_REVIEW`, `REJECTED`, and `HIDDEN` media stay excluded.
- Public timeline responses use short-lived presigned playback URLs.
- Public timeline responses use `Cache-Control: no-store` because they contain
  expiring URLs.
- Admin approval rejects approved object references outside the configured
  storage base URL.
- Admin moderation actions are audited in the same transaction as the state
  transition.

## MVP Limited-Launch Policy

For the first limited MVP launch, automatic malware scanning is not required to
run inline with upload completion. Instead, media publication depends on a
manual operator-controlled review process.

The limited-launch process is acceptable only while all of the following
conditions are true:

- Upload volume is low enough for every uploaded asset to be reviewed by an
  admin before approval.
- Original uploads remain private and are accessible only through short-lived
  admin preview URLs.
- Public playback remains limited to admin-approved media.
- Admins do not approve media that cannot be safely previewed.
- Admins can reject or hide problematic media immediately.
- The platform owner accepts the residual risk that manual review is weaker
  than automatic malware scanning.

This policy does not claim that uploaded media is malware-free. It means the
system prevents unreviewed uploads from reaching the public timeline and uses
operator review as the MVP safety gate.

## Admin Review Procedure

Before approving media, an admin should:

1. Confirm the media belongs to the expected ownership range.
2. Confirm the media type, duration, and visible content match the purchased
   range and platform rules.
3. Preview original media only through the short-lived admin preview action.
4. Avoid downloading original files to a personal workstation unless review
   requires it.
5. If local inspection is required, use a hardened review machine or sandboxed
   viewer with current operating system and browser security updates.
6. Reject any file that fails to preview normally, behaves unexpectedly, or
   appears to contain executable, archive, document, HTML, SVG, or script
   content.
7. Reject media that violates platform rules, copyright policy, or user safety
   rules.
8. Approve only media that is safe to publish in the public timeline.

Admins must use `REJECTED` for media that should never be published and
`HIDDEN` for previously approved media that must be removed from the public
timeline.

## Automatic Scanning Decision

Automatic scanning is deferred for the MVP limited launch because a resident
scanner such as ClamAV increases memory, CPU, signature-update, and operational
maintenance cost on the selected `t4g.medium` EC2 baseline.

Automatic malware scanning becomes required before any of the following:

- open self-service launch with material upload volume;
- reducing or removing admin review before publication;
- allowing additional file types beyond the current image and MP4 policy;
- generating thumbnails, transcodes, or derived media from arbitrary uploads;
- serving original uploads through a public bucket, CDN, or long-lived URL;
- accepting enterprise, advertiser, or paid-user commitments that require a
  stronger media safety statement.

The preferred future design is asynchronous scanning:

- Upload completion creates media in a non-public state.
- A scanning worker reads the private object through the storage port.
- Scan results are recorded before approval or publication.
- Approval is allowed only after the scan passes.
- Scan failure transitions media to a rejected or quarantine state.
- Scan result metadata is auditable but does not expose sensitive scanner
  internals to public APIs.

The scanning implementation should use a port in the application layer and an
adapter for the scanner so the domain does not depend on ClamAV, a vendor API,
or scanner-specific models.

## Licensing And Dependency Policy

Do not add GPL or AGPL scanner dependencies or container images without
explicit approval. If ClamAV is selected, verify the exact image and bundled
components before adoption and document the license review in the implementation
plan.

Acceptable first choices are:

- a permissively licensed scanner deployment with documented image provenance;
- a vendor scanning API with a clear data-processing agreement and cost model;
- an isolated operator-run scanning process for the limited MVP launch.

## Operational Evidence

Before marking media safety ready for a limited launch, keep evidence that:

- local media upload verification passes;
- staging media preview smoke passes;
- staging media duration smoke passes;
- staging media signature smoke passes;
- staging presigned upload CORS smoke passes;
- admin moderation smoke passes;
- admins can reject and hide media;
- Cloudflare cache bypass remains active for API responses with presigned URLs.

## Incident Response

If unsafe media is reported or discovered:

1. Hide the media immediately.
2. Preserve the media asset ID, ownership record ID, request ID, uploader
   account, and audit log entries.
3. Revoke or rotate any exposed preview or playback URL by waiting for expiry
   and avoiding further presigned URL generation.
4. Review the uploader account and related uploads.
5. If storage object deletion is required, treat it as a data operation and
   record the object key, reason, actor, and rollback limitations.
6. Update platform rules, admin review guidance, or automated scanning
   requirements if the incident exposes a policy gap.

## Release Gate

For a limited MVP launch, media safety can be considered ready when the
implemented upload validation controls pass staging verification and the manual
admin review process is accepted by the project owner.

For a broader public or paid launch, automatic malware scanning or an explicitly
accepted risk exception must be in place before reducing admin review or
increasing upload volume.
